# 比赛计时系统 Constitution

## Core Principles

### I. 架构与代码质量原则 (Architecture & Code Quality Principles)

**MUST遵循以下规则：**

1. **清晰的分层架构**：严格分离表示层（WPF UI）、业务逻辑层、数据访问层
   - 每一层应该通过明确定义的接口进行通信
   - 禁止跨层直接调用（如表示层直接调用数据访问层），相邻层之间可以通过接口或直接调用
   - 业务逻辑层必须独立于UI框架，便于测试和维护

2. **MVVM模式驱动**：使用MVVM模式实现视图与逻辑分离
   - 使用 CommunityToolkit.Mvvm 作为MVVM框架
   - ViewModel 负责业务逻辑和状态管理，View 只负责展示
   - 业务逻辑依赖必须通过构造函数注入，禁止静态方法和单例模式
   - 工具类和纯函数可以使用静态方法（如：时间格式化、数据校验、类型转换）
   - 基础设施单例（如：日志记录器、配置管理器、数据库连接）可以使用单例模式，但必须通过接口访问
   - 核心业务组件应该支持可替换的实现（如：设备服务、计时服务）

3. **单一职责原则**：每个类不超过500行代码，专注于单一功能
   - 超过500行的类应该拆分为多个协作类
   - 每个类的职责应该清晰明确（通过类名和代码结构体现）
   - 复杂业务逻辑应该拆分为多个服务类协作完成

4. **人类可读代码**：避免过度优化，优先考虑可读性和可维护性
   - 代码应该自文档化，关键逻辑应该有注释说明意图
   - 命名应该清晰表达意图，避免缩写和隐晦命名
   - 时间计算、设备通信等关键逻辑必须有详细注释

5. **显式依赖**：业务逻辑依赖必须通过构造函数注入
   - 禁止在业务逻辑中使用全局状态和静态变量
   - 工具类和纯函数可以使用静态方法
   - 基础设施服务可以使用单例，但必须通过依赖注入容器管理
   - 关键外部依赖应该通过接口抽象（设备服务、数据库服务、日志服务）

**Rationale**: 清晰的分层和MVVM模式确保代码可维护、可测试、可扩展。单一职责和可读性保证长期维护成本可控，特别是在需要快速定位和修复生产问题时。

### II. 测试与调试标准 (Testing & Debugging Standards)

**MUST遵循以下规则：**

1. **单元测试优先**：所有核心逻辑必须有单元测试，覆盖率>80%
   - 所有业务逻辑类必须达到80%以上的代码覆盖率
   - 关键路径和边界条件必须有测试覆盖（计时逻辑、数据校验、设备通信）
   - 计时精度相关的逻辑必须有专门的测试用例

2. **可测试性设计**：核心设备交互和计时逻辑应该通过接口抽象，便于模拟和测试
   - 设备扫描服务应该封装在可模拟的接口中，支持模拟设备进行测试
   - 计时服务应该可以独立测试，不依赖实际UI
   - 数据库操作应该通过仓储模式抽象，支持内存数据库测试
   - 简单的工具函数和只读查询可以例外

3. **调试友好**：提供详细的日志分级（Trace/Debug/Info/Warn/Error）
   - 关键操作应该记录日志（设备扫描、计时开始/结束、数据导入导出）
   - 日志应该包含足够的上下文信息（时间戳、操作类型、相关参数、用户操作）
   - 设备通信日志必须详细记录，便于排查硬件问题
   - 日志按天rotate，详细日志保留90天，错误日志单独文件保留

4. **诊断工具**：内置运行时诊断和状态检查功能
   - 应该提供设备连接状态检查功能
   - 应该提供数据库健康检查功能
   - 应该提供计时器状态查询功能
   - 日志文件应该可以通过Navicat等工具直接查看数据库

5. **失败可追溯**：异常应该包含足够的上下文信息
   - 异常消息应该包含操作上下文、失败原因和可能的解决方案
   - 异常应该记录到日志系统
   - 数据导入失败应该明确指出失败的行号和原因
   - 设备通信失败应该记录详细的错误信息

**Rationale**: 高测试覆盖率确保代码质量，可测试性设计保证测试效率，详细的日志和诊断工具加速问题定位，特别是在比赛现场需要快速排查问题时。

### III. 用户体验一致性 (User Experience Consistency)

**MUST遵循以下规则：**

1. **渐进式交互**：复杂操作分步引导，避免一次性配置过多
   - 多步骤操作应该提供清晰的进度指示（数据导入、设备配置）
   - 每个步骤应该提供明确的说明和验证
   - 比赛分组添加应该分步引导，避免一次性填写过多信息

2. **状态可视化**：及时显示比赛状态和设备状态
   - UI应该及时反映比赛的实际状态（待开始、待发令、比赛中、已完成）
   - 设备连接状态应该实时显示（激活/暂停）
   - 计时面板应该实时更新，显示当前计时和圈数
   - 完成人员应该用绿色背景高亮显示

3. **操作反馈**：所有操作都有明确的反馈提示
   - 成功操作应该有Toast提示
   - 失败操作应该有明确的错误提示和解决建议
   - 长时间操作（数据导入、导出）应该显示进度条
   - 设备连通测试应该有明确的成功/失败反馈

4. **数据安全**：提供数据备份和恢复功能
   - 关键操作（删除分组、清除设备）应该有二次确认
   - 应该支持数据导出备份
   - 数据导入应该有校验和回滚机制

5. **错误指导**：错误信息附带具体的解决步骤
   - 错误消息应该包含可操作的解决建议
   - 常见错误应该提供快速修复选项
   - 数据导入错误应该明确指出哪一行、哪一列有问题
   - 设备连接错误应该提供排查步骤

**Rationale**: 渐进式交互降低用户认知负担，状态可视化增强用户信心，操作反馈和错误指导保障用户在比赛现场能够顺利操作。

### IV. 性能与可扩展性要求 (Performance & Scalability Requirements)

**MUST遵循以下规则：**

1. **响应式架构**：UI线程不阻塞，长时间操作异步执行
   - 明显影响用户体验的耗时操作（>200ms或用户可感知的延迟）应该在后台线程执行
   - UI应该提供操作进度反馈（对于长时间操作，如数据导入、Excel导出）
   - 设备扫描事件应该在后台线程处理，避免阻塞UI
   - 数据库查询应该在后台线程执行

2. **实时性要求**：毫秒级计时精度，实时状态更新
   - 计时器必须使用高精度计时器（Stopwatch），精度到毫秒
   - 设备扫描事件必须实时处理，延迟<100ms
   - UI更新应该使用Dispatcher.BeginInvoke，避免阻塞计时线程
   - 多组并发计时时，每个组的计时应该独立线程管理

3. **资源高效**：及时释放数据库连接和设备资源
   - 所有数据库连接必须在使用后及时释放，使用using语句
   - 设备连接应该实现IDisposable模式确保资源清理
   - 大量数据查询应该使用分页，避免一次性加载过多数据
   - 日志文件应该按天rotate，避免单个文件过大

4. **模块化设计**：核心功能与扩展功能分离
   - 核心计时功能必须独立于UI和扩展功能
   - 设备服务应该通过接口抽象，支持不同设备实现
   - 数据导入导出功能应该模块化，便于扩展支持其他格式
   - 小型扩展可以通过配置实现，不强制插件机制

5. **配置驱动**：关键参数外部化，支持配置管理
   - 关键配置参数应该可从外部文件加载（数据库路径、日志路径、设备配置）
   - 配置变更应该支持运行时重载（如适用，对于不支持热重载的配置应明确说明）
   - 文件存储路径应该可配置（data、logs目录）

**Rationale**: 响应式架构保证用户体验，实时性要求确保计时精度，资源高效使用避免系统问题，模块化和配置驱动支持长期演进。

### V. 数据管理与一致性要求 (Data Management & Consistency Requirements)

**MUST遵循以下规则：**

1. **数据校验严格**：所有数据导入和操作必须严格校验
   - Excel导入必须校验所有必填字段、格式、重复性
   - 日期格式必须支持三种格式：YYYY-MM-DD、YYYY-MM-DD上午、YYYY-MM-DD下午
   - 序号必须从1开始的连续数字
   - 重复数据必须拒绝导入，并明确提示错误原因
   - 芯片分配必须确保不重复分配

2. **事务性操作**：关键数据操作应该支持事务和回滚
   - 数据导入应该使用事务，失败时自动回滚
   - 芯片分配操作应该支持事务，确保数据一致性
   - 比赛成绩记录应该支持事务，避免部分数据丢失
   - 失败时应该尝试自动回滚，如果自动回滚不可行，必须提供手动恢复机制

3. **数据可追溯**：所有关键操作应该记录到数据库
   - 设备扫描记录应该保存到数据库，便于追溯
   - 比赛成绩应该完整记录，包含开始时间、结束时间、计时等
   - 数据导入导出操作应该记录日志
   - 数据库应该支持通过Navicat等工具直接查看和SQL查询

4. **数据备份**：提供数据导出和备份功能
   - 应该支持成绩数据导出为Excel
   - 应该支持数据库备份功能
   - 导出文件应该包含完整的表头和格式化内容
   - 导出Excel应该使用文本格式，避免显示错误

5. **数据一致性**：确保数据在不同模块间的一致性
   - 人员分组、芯片分配、比赛计时之间的数据应该保持一致
   - 芯片组颜色应该在所有相关界面同步显示
   - 比赛状态应该在所有相关组件间实时同步

**Rationale**: 严格的数据校验和事务处理确保数据准确性，数据可追溯支持问题排查，数据一致性保证用户体验。

### VI. 设备集成与实时性要求 (Device Integration & Real-time Requirements)

**MUST遵循以下规则：**

1. **设备抽象**：设备服务应该通过接口抽象，支持模拟和真实设备
   - 扫描设备服务应该通过接口抽象，便于测试和切换实现
   - 应该支持模拟设备进行开发和测试
   - 真实设备集成应该独立封装，不影响核心业务逻辑
   - 设备连接失败应该有优雅降级，不影响其他功能

2. **实时扫描处理**：设备扫描事件必须实时处理
   - 扫描事件应该在后台线程处理，避免阻塞UI
   - 扫描去重：同一芯片短时间内多次扫描只计一次（建议去重窗口：500ms）
   - 扫描事件应该立即更新UI，延迟<100ms
   - 设备通信日志应该实时显示，支持上下键浏览历史

3. **多组并发控制**：支持多组同时计时，但需要控制开跑间隔
   - 每个组的计时应该独立管理，互不干扰
   - 开跑时应该检查分组间隔，确保间隔≥10秒
   - 使用SemaphoreSlim等机制控制并发开跑
   - 每个组的状态应该独立维护

4. **设备状态管理**：设备状态应该实时同步
   - 设备激活/暂停状态应该实时更新
   - 设备连通测试应该异步执行，不阻塞UI
   - 设备连接失败应该有重试机制
   - 设备状态变更应该记录日志

5. **优雅降级**：当设备不可用时提供替代方案
   - 设备连接失败时应该提供手动计时选项（如适用）
   - 应该支持模拟设备模式进行测试
   - 设备服务不可用时，其他功能应该正常工作

**Rationale**: 设备抽象支持灵活的设备集成，实时处理确保计时准确性，多组并发控制保证比赛公平性，优雅降级提高系统可用性。

## Governance

本宪法文件是项目的最高指导原则，所有开发活动必须遵循本宪法。宪法优先于所有其他实践和约定。

### 修订程序

- **修订提案**：任何团队成员可以提出宪法修订提案
- **修订审查**：修订必须经过团队审查和批准
- **版本管理**：遵循语义化版本控制（MAJOR.MINOR.PATCH）
  - MAJOR：向后不兼容的原则移除或重新定义
  - MINOR：新增原则或重大扩展指导
  - PATCH：澄清、措辞修正、非语义性改进
- **迁移计划**：重大修订必须包含迁移计划和兼容性说明

### 合规审查

- **代码审查**：所有PR必须验证是否符合宪法原则
- **架构审查**：重大架构决策必须对照宪法进行审查
- **测试审查**：测试覆盖率必须满足宪法要求
- **复杂度审查**：任何违反单一职责原则的代码必须提供充分理由

### 合规检查点

在以下阶段必须进行宪法合规检查：

1. **Phase 0 (研究阶段)**：架构设计必须符合分层架构原则
2. **Phase 1 (设计阶段)**：数据模型和接口设计必须符合可测试性原则
3. **Phase 2 (实现阶段)**：代码实现必须符合所有代码质量原则
4. **Phase 3 (测试阶段)**：测试覆盖率必须达到80%以上
5. **Phase 4 (部署阶段)**：用户体验和性能要求必须得到验证
